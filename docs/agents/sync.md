# Storage and cloud sync

localStorage persistence, Supabase sync and merge, auth init. Read before touching `storage.js`, `auth.js`, `syncState`, or the sync UI on build.html.

## Storage

`syncState` is local-only merge metadata, not part of the PRISM domain model. Baseline shape per prism: `{ updatedAt, deckUpdatedAts, splitGroupUpdatedAts, deletedDecks, deletedSplitGroups, plannedSwapUpdatedAts, deletedPlannedSwaps }`

localStorage key: `prism_data`. Structure: `{ version, currentPrismId, prisms: { [id]: prismData }, preferences, syncState }`. `syncState` stores per-prism sync baselines plus local deletion tombstones so multi-device merges can distinguish local edits from local deletes. Un-marks are not in it: they sync with the PRISM (`markTimes`, below). Version migrations supported. Supabase sync happens optionally on auth state changes and on debounced saves while authenticated. `getPreferences()` merges with defaults so new preference keys auto-populate for existing users.

Sync behavior is merge-first, not whole-PRISM last-write-wins:

- On login/session restore, local and cloud PRISMs are merged per prism, per deck, and per split group.
- `markedCards` merge per key on `markTimes` (#500): `{ [cardKey]: isoTime }`, when the key was last marked or un-marked on any device (a key in `markedCards` was marked then, a key not in it was un-marked then). `mergeMarks` keeps, per key, the side with the newer time, so an un-mark (manual checkbox, bulk clear, or an auto-unmark like `unmarkCardsWithNewStripes`) reaches a device that still holds the mark, and a re-mark beats an older un-mark. A key with no time on either side (marked before #500) stays marked if either side holds it, as the old union did; equal times keep it marked too. `markTimes` take the newer time per key. `savePrism` writes the times itself (`recordLocalPrismChanges`): every key the save adds to or drops from `markedCards`, compared with storage, gets the wall clock, and no key's time goes back (the save's times and storage's, newer per key), so a copy without times (a backup restored over the PRISM through `buildPrismFromJson`, a rebased stale page) keeps storage's. Callers just save; there is no tombstone call. Column `prisms.mark_times` (JSONB NOT NULL DEFAULT '{}'), mapped in `buildPrismFromRow` and the prism upsert; rollout is schema-first, since `PRISM_SELECT` reads it. Never pruned: an un-mark must outlive every stale copy that holds the mark. Before #500 an un-mark waited for sync as a device-only tombstone in the baseline (`unmarkedCards`); `loadStorage` folds any left over into `markTimes` (`foldLegacyUnmarks`) and drops the field. Known limits: device clocks decide, so a fast clock on one device wins two changes to the same key (#502; changes to different keys are unaffected). During rollout, a client still running the old code uploads `marked_cards` without touching `mark_times`, so its un-mark ties with the other device's mark time and the mark stays (the old #500 behaviour), and a mark it made offline syncs later with no time, so it loses to an un-mark of that key another device timed. Both end once every device has reloaded. Tests: the marks scenarios in `tests/sync-two-device.test.js`.
- `removedCards` merge by `(cardName, deckId)` with latest `removedAt`; `previousQuantity` keeps the max of both rows so successive quantity edits never under-report the surplus. `clearedQuantity` (#376, copies a Sleeve reuse already cleared) and `sleeveSwappedQuantity` (#401, copies a Sleeve swap moved out of the card while the row was open) also keep the max of both rows. A row is done when `clearedQuantity ≥ previousQuantity − newQuantity` (`removalOpenCopies` in swap.js is 0) and is hidden from Marks to Clear, not deleted: a deleted row would come back from the other device's copy (#501). Every path that finishes a row (Clear, Clear all, `autoClearRemovedCards`, `clearReturnedRemovals`, `trackStaleChildMarks`) closes it with `closeRemoval` (swap.js), which raises `clearedQuantity` to the open copies; none drops it. Both fields only go up, so merging in either order gives the same row. A card removed again after its row closed is a new removal: `trackRemovedCard` writes a fresh row (nothing carried) with `generation` one higher, and `mergeRemovedCards` takes the higher generation whole, so the closed copy on another device can't close it. `trackRemovedCard` carries `clearedQuantity` onto a re-tracked open row. `clearReturnedRemovals` looks only at open rows (a closed row's mark was cleared, or its card already came back) and skips an open row with `clearedQuantity` (partly cleared: a Sleeve reuse, or a Clear merged in from another device, so its mark isn't on every copy). The field rides the `prisms.removed_cards` JSONB, so it needs no column or storage mapping. So does `splitGroup`, the group a split variant's row records as painted (latest row wins).
- `useDedicatedCommanderCopies` merges on its own `useDedicatedCommanderCopiesUpdatedAt` (newer wins, ties local) — explicitly, in `mergePrismVersions`, like `markedCardsUpdatedAt`. The Supabase columns are `use_dedicated_commander_copies` (NOT NULL DEFAULT false) + `use_dedicated_commander_copies_updated_at`; rollout was schema-first.
- `plannedSwaps` (the Swap Queue, #364) live in their own table, `planned_swaps` (one row per Planned swap, owner-only RLS through the prism, INSERT gated on `is_entitled()`, `deck_id` cascades with the deck). Rollout was schema-first: `PRISM_SELECT` embeds the table, so a missing table fails every cloud read. They merge in `mergePlannedSwaps` (called from `mergePrismVersions`) per id, newer `updatedAt` wins, never via `basePrism`. Unlike `mergeEntityCollection`, removal always beats an edit, since an applied swap that came back could be applied twice: removing or applying one writes `baseline.deletedPlannedSwaps[id]` (wall clock — queue edits don't bump `prism.updatedAt`) in `recordLocalPrismChanges`, and a tombstoned id never returns from the cloud; a local swap the baseline (`plannedSwapUpdatedAts`) shows as synced, but the cloud no longer holds, was removed elsewhere and is dropped even if edited here since. `savePrismToSupabase` upserts the queue after the decks, skipping swaps whose deck is gone, and deletes only rows it has evidence it removed (a `deletedPlannedSwaps` tombstone, or an id in `plannedSwapUpdatedAts` no longer queued) — never "every row not queued here", which would delete a swap another device queued after this save's merge (the Swap Queue page drops those with a tombstone). A Lapse pauses writes like any other, so nothing is deleted.
- `tokenChoices` (the Token pack, #412) live in their own table, `token_choices` (PK `(prism_id, kind, oracle_id, deck_id)`, `deck_id` '' off `added`, owner-only RLS through the prism, no `is_entitled()` gate — the pack is free; cascades with the prism; `deck_id` has no foreign key, so a row for a deck deleted elsewhere still saves). Rollout is schema-first: `PRISM_SELECT` embeds the table, so a missing table fails every cloud read. One entry per (kind, Token type, deck): `added` (one deck: `deck_id`, `name`, `included`; false = unticked), `paired` (`paired_with`; NULL = unpaired; a pair stands only while both sides point at each other), `hidden` (boolean). `TOKEN_CHOICE_FIELDS` (tokens.js) maps each kind's fields to columns for `buildPrismFromRow`, the upsert and the backup import. They merge in `mergeTokenChoices` (called from `mergePrismVersions`) per `tokenChoiceKey` (kind, oracleId, deckId), newer `updatedAt` wins, ties local, never via `basePrism` and with no baseline. A deck tick is its own entry, so two devices ticking two decks for one token keep both. Nothing is ever deleted: undoing a choice writes a newer entry, and `savePrismToSupabase` only upserts them. So a copy that lacks an entry — the other device's older copy, or a build page holding a stale PRISM (#499) — has nothing to delete, and the newest choice on any device wins on every device (no local-only tombstone, unlike #500). Tests: the Token pack scenarios in `tests/sync-two-device.test.js`, RLS in `tests/token-choices.sql`. Known limits: per-entry last-writer-wins on device clocks (#502 skew applies to two edits of the same entry); a stale build page shows other-device choices only after reload (#499's display half). Token Done ticks are ordinary `markedCards` keys (`token:` prefix) and share their merge (`markTimes`).
- Card row `isSideboard` (#29) is column `deck_cards.is_sideboard` (BOOLEAN DEFAULT false), written by `replace_deck_cards` (and the fallback insert), mapped in `buildPrismFromRow` (only `true` lands, as `isSideboard: true`). Like `sleeve`, it rides the deck's `updatedAt`, with no merge branch. Rollout is schema-first: `PRISM_SELECT` reads the column.
- Deck `sourceUrl` (#377) is column `decks.source_url` (nullable TEXT), mapped in `buildPrismFromRow` and the deck upsert. It rides the deck's `updatedAt` through `mergeEntityCollection`, with no merge branch of its own. Rollout is schema-first: `PRISM_SELECT` reads the column, so a missing column fails every cloud read. Details in `docs/agents/deck-export.md`.
- Background saves fetch the latest cloud copy, merge it with local using the stored baseline, then write the merged result back to Supabase.
- **A save from a stale snapshot rebases onto storage** (#499). build.html holds `state.currentPrism` across background merges, and a second tab writes the same storage, so the copy a caller saves can be older than storage. `getCurrentPrism`/`getPrism` stamp the PRISM they return with the storage string they read it from (`READ_AS`, a Symbol: it rides the processor's spreads and `clonePrism`, never reaches JSON; no stringify per read), and `savePrism` re-stamps the caller's copy after each save. When the storage string changed and its PRISM no longer equals the stamped one (compared ignoring key order), `savePrism` saves `rebasePrism(stamp, caller, storage)`: storage's copy plus only what the caller changed since its stamp. Decks, split groups, Planned swaps and marks go by id (the caller's adds and removals; edited on both sides, the newer `updatedAt` wins, ties the caller, as in `mergeEntityCollection`; a deck the caller edited beats its removal elsewhere, a Planned swap never does), Marks to Clear and Token pack choices through their own merges, `updatedAt`/`markedCardsUpdatedAt` take the newer, `markTimes` newer per key of the caller's and storage's, then the rebased save's changes timed (`recordLocalPrismChanges`), `useDedicatedCommanderCopies` goes by its own timestamp, any other field (name) only when the caller changed it. So tombstones go only to what the caller removed, never to what it never saw, and a deck removed elsewhere is not saved back. `applySwap`/`completeReuse` copy with `clonePrism` (core/utils.js), since `structuredClone` drops Symbol keys. An unstamped copy (`getAllPrisms`, `createPrism`) is saved as is, as before. Known limit: the open page shows the other device's changes only after a reload.
- Deck and split-group `updatedAt` timestamps are important for conflict resolution and should be preserved on mutation.
- Split-group child ordering should be preserved from `group.childDeckIds` during merge; only orphaned child IDs should be dropped, with deck-derived order used as a fallback when the stored ordering is missing.
- Auto-created empty PRISMs (no decks, no cards, no prior baseline) are **not** uploaded to Supabase during the login sync — they exist only as a pre-login UI placeholder and are discarded when real cloud data is available.
- `syncWithSupabase` tracks which prisms have genuine local changes (`needsCloudWrite` set) and only writes those. Cloud-only prisms (fresh device load) have their baseline recorded without re-uploading, preventing redundant `replace_deck_cards` calls.
- `savePrismToSupabase` continues past per-deck RPC failures so one failing deck does not leave all subsequent decks without cards. It returns `false` when any deck fails so the baseline is not recorded and the sync retries. `importAllData` routes each imported PRISM through `syncPrismToSupabase` for the same reason — a baseline recorded before the upload would make a failed import read as already-synced.
- **Cloud writes pause on a lapse; cloud reads never do** (#212). Pull paths (`syncWithSupabase`, `loadPrismsFromSupabase`) gate on `shouldSyncToSupabase()`; every upload, cloud delete and debounced drain gates on `shouldWriteToSupabase()` — which is `shouldSyncToSupabase() && !cloudWritesPaused`. `cloudWritesPaused` is refreshed from `isEntitled()` once per page load, at the top of `syncWithSupabase`, and fails open. Auth publishes the user before that verdict lands, so the paths that write immediately (`syncPrismToSupabase`, `forceSyncCurrentPrism`, `deletePrism`) gate on `canWriteToSupabase()` instead — it awaits the in-flight read, then answers. The debounce keeps queueing on `shouldWriteToSupabase()` so an edit made mid-verdict is deferred, never dropped; the drain re-checks. While paused, a prism with local changes is skipped **including its baseline**: the baseline must keep describing what the cloud really holds, since it is both the merge reference and the date the paused notice shows. Exports: `isCloudWritePaused()`, `getLastCloudSyncDate(prismId?)`.
- **25 cloud PRISMs per account** (#209), enforced by the `prisms` INSERT policy, which counts the owner's *other* PRISMs so an upsert of an existing one still saves at the cap. A `42501` on the prism upsert for a PRISM with no cloud baseline is read as the cap: `savePrismToSupabase` adds it to `localOnlyPrismIds`, it is not retried this page load (Sync Now clears it and retries), and `#local-only-notice` on build.html says it lives on this device. Export: `isPrismLocalOnly(prismId)`.

## Auth Double-Init

`initAuth()` caches its async body as `authInitPromise`. Both `layout.js` and page scripts can call it safely and will await the same Promise — including the initial `syncWithSupabase()` — so cloud merge always completes before any caller proceeds. `setupAuthListeners()` is separate and handles UI updates. It calls `updateAuthUI(currentUser)` at the end so the nav reflects auth state immediately, since `INITIAL_SESSION` from Supabase can fire before listeners are registered when the session is already in memory.

If the Supabase CDN hasn't loaded when `initAuth()` runs, it awaits the script's `load` event (5s timeout fallback). If `getSupabase()` still returns null after the wait (CDN error/timeout), `authInitPromise` is reset to `null` so callers can retry — without this reset, a resolved-null promise would permanently block re-initialization.

## Supabase Card Sync

`savePrismToSupabase()` upserts the PRISM row, the decks, each deck's cards, Planned swaps and Token pack choices, in that order. It replaces all cards for each deck via the `replace_deck_cards(p_deck_id, p_cards, p_created_at)` RPC defined in `supabase-schema.sql`. The RPC runs DELETE + INSERT in a single transaction, preventing a partial-failure window where a deck could be left with no cards. Pass an empty array to clear cards safely. Deck rows go up first with their old cloud `updated_at` (epoch for a new deck) and get the real one in a second upsert only after their cards save, so a device pulling between a failed card write and the retry never takes the new timestamp with the old cards (#503). Uses `SECURITY INVOKER` so existing RLS on `deck_cards` applies — users cannot replace cards in decks they don't own. Run `supabase-schema.sql` in the Supabase SQL editor after any schema changes.

The deck-card loop uses **continue-on-error**: a failing RPC for one deck is logged but does not abort the loop. All decks are attempted. If any deck failed, `savePrismToSupabase` returns `false` so `recordPrismBaseline` is not called and the next debounced save retries.

**No `updated_at` triggers on `prisms` or `decks`.** The client always supplies `updated_at` on upsert. A server-side trigger that overwrites it with `now()` (server clock) causes clock-skew bugs: `cloud.updated_at` ends up ahead of `local.updatedAt`, so `mergeEntityCollection` in `syncPrismToSupabase` silently picks the stale cloud deck and reverts user edits on the next page load. The schema includes an idempotent `BEGIN/COMMIT` migration block to drop those triggers on existing deployments.

## Merge Conflict Resolution

`mergeEntityCollection` handles three cases per entity ID:
- **Both local and cloud present:** if `local.updatedAt > baseline.updatedAt` for that entity, local wins (user edited since last sync — guards against server-clock-ahead skew). Otherwise, `pickNewerEntity` compares timestamps. A baseline can carry another device's clock, so `savePrism` (`recordLocalPrismChanges`) stamps every local change after the version it replaces (`stampAfter`: 1 ms past it when this clock is behind): a deck or split group whose `updatedAt` the save changed, a deck/group delete tombstone, and each changed key's `markTimes` entry (#502). A device whose clock is behind still reads as edited since the last sync; concurrent edits on both devices still fall back to timestamp comparison.
- **Local only:** kept if `local.updatedAt > baseline.updatedAt`, otherwise treated as deleted on another device.
- **Cloud only:** kept unless locally deleted after the cloud's `updatedAt`.

**markedCards:** merged per key by `mergeMarks` on `markTimes` (see Storage above). An un-mark and re-mark inside one debounce keeps the mark (#416): the re-mark is the newer time. `unmarkCardsWithNewStripes` still returns the keys it un-marked (deck edits count them for the toast), and `applySwap`/`completeReuse` report theirs (`summary.unmarkedKeys`, `unmarkedKeys`, asserted in tests); nothing needs them to sync.

## Sync UI on build.html

- `build.html` has a sync status indicator (`#sync-status`) and a Sync Now button (`#btn-sync-now`) near the PRISM name; both are hidden until the user is logged in. `setupSyncStatus()` in `init.js` wires these to `onSyncStatusChange` / `forceSyncCurrentPrism` from `storage.js`. Storage exports: `onSyncStatusChange(cb)` (returns unsubscribe fn), `forceSyncCurrentPrism()`
- The paused-sync notice (`#sync-paused-notice` on build.html, the profile Subscription caption) is shown only when writes are paused **and** a last-sync date exists — with no cloud copy there is no sync to pause, and the notice would claim one. Its dated sentence has one source, `pausedSyncDetail()` in `core/utils.js`; the wording is fixed by CONTEXT.md (*paused*, never frozen or locked, always dated). `renderAll()` re-renders it because the date is per-PRISM
